# 性能可疑点清单（待设备空闲时验证）

> 本文件记录**尚未被测量证实**的性能判断。每条注明：现状、怀疑理由、怎么验、
> 验证后的结论该写回哪里。测完就删掉对应条目。

## 已修（留作记录，避免回退）

| 问题 | 修法 |
|---|---|
| `range` 上界的线性探上限按窗口大小取（`linear_max*8=64`），导致 64 元窗口被扫两遍 | 改成常量 8：窗口 ≤8 走线性探，>8 回退 `upper_bound_fast` |
| `len()` 每次都遍历 chunks 求和（旧 chunked 版） | 已随结构简化消失（现在是 `entries.len()`） |
| 追加快路径缺失 | 升序插入直接 `Vec::push`，省一次二分 |
| 删末尾没有快速路径 | 末元素相等时直接 `Vec::pop`（按序回滚/清理的形态） |
| `cursor_lower_bound` 命中后仍进"向左找"分支 | 短路 `Equal` |
| `Clone` 会让游标 `id` 复用（潜在正确性坑） | 已写入 struct 文档：加 `Clone` 必须换新 `id` |

## 待验证

1. **`RANGE_SCAN_MAX = 8` 是否最优**
   - 现状：固定 8；怀疑点：该值应≈一次块内二分的比较次数，块内元素分布不同时最优点会漂。
   - 验法：把它做成 `with_span_scan_max(n)` 临时参数，对 `--win` ∈ {8, 64, 1024} × 两种分布扫 0/4/8/16/32。
   - 状态：成对交替测量下**没有可分辨差异**（见 `docs/validation.md`），默认 8 保留；
     若要继续，只能在更稳的机器上放大窗口（`--win 1024`）重测。

2. **块表大小与 L1/L2 的冲突**
   - 现状：块数 ≈ n（`W ≈ span/n`），n=1e5 时块表 ≈ 390 KB、n=1e6 时 ≈ 4 MB。
   - 工具：`with_width_scale(k)` + `bench --sweep <n>`（只跑参数扫描，秒级）。
   - 状态：**已验，无收益**。n=100k 与 n=1M 的 scale 0.5–8 扫描里，随机查询
     没有单调趋势（1M 稀疏：23.8 / 50.8 / 37.2 / 34.7 / 29.6 ns，纯噪声级起伏），
     聚簇数据全在 12–15 ns。结论：块表即使超出缓存也不是瓶颈（点查询同时还要
     访问条目数组），**不做自适应块宽**。

3. **聚簇块内二分能否再降**
   - 现状：块内元素 > `linear_max` 时块内二分（约 7 次比较）。
   - 怀疑：加二级锚（每块 8 格）可把定位降到 1 次加载 + ≤8 项线性扫。
   - 状态：未实现，未测。

4. **`block_of` 的 f64 除法**
   - 现状：每次查询一次 `(k - base) / width`。
   - 怀疑：`W` 是 2 的幂，除以 2^k 在 f64 上是精确缩放；可换乘 `inv_width`，但需证明
     分块边界完全一致（否则会出现极罕见的错块）。
   - 状态：未实现，未测。

5. **`cursor_lower_bound/upper_bound` 的双比较循环**
   - 现状：循环条件比较一次，循环退出后再比较一次判断是否超限。
   - 状态：未改；成对测量下顺序查询已明显占优，先不动。

6. **`RangeIter` 与 `slice::Iter` 的差别**
   - 现状：`window_split` 的 iter 列两者相同（同一量级），`split_first` 没有额外成本。
   - 状态：已验证无差异，不必改。

7. **插入的 memmove**
   - 现状：任意位置插入 O(n)；升序追加已走快路径。
   - 状态：`ins` 两档同量级；批量导入可用 `extend_sorted`。

8. **时间窗负载缺失**
   - 现状：bench 的窗口按**元素序号**切，聚簇时会切在块中部（对抗性）。
   - 状态：未加；游标收益可能被低估。

9. **块表的宽度**（u16 变体）
   - 状态：未实现；若块表不是瓶颈（见第 2 条）则收益有限。

10. **线性扫里每个元素的比较成本**（`total_cmp` vs `<`）
    - 状态：未测；只在扫描长度变大时才有意义。

11. **脏索引期间的查询**
    - 现状：任一写入后所有查询都走全表二分，直到显式 `rebuild()`。
    - 状态：未测；取决于编辑-查询节奏。

12. ~~**随机删除 Vec 约快 2×**~~
    - **已查**：那是未成对测量（先测完一档再测另一档）造成的偏差。把建表/插入/删除
      也改成同一轮内交替测量后，n=1e5 的删除是 Jump 80–89 ns vs Vec 142–155 ns，
      Jump 反而略快。结论：**无差距**，不再处理。

12. ~~**`range_end_from` 的 hi 与 lo 同块时**~~
    - **已修**：大步路径改成"直接用 `hi` 所在块定位"：`b = block_of(hi)` →
      `block_span(b)` → 块尾元素 ≥ hi 时在 `[max(from,start), end)` 内二分；
      块尾 < hi 时答案就是 `end`（`end` 之后的首元素 key ≥ 下一块起点 > hi）。
      省掉原来"扫 8 项 + 再 `upper_bound_fast` 重新 block_of"的一次除法与块表加载。
      边界测试：`range_upper_bound_crosses_blocks`（跨块/超末尾/空区间/同块）。

## 测量方法本身的坑（先修这个，再信数字）

- 当前 `bench` 每轮先跑固定 CPU 负载（probe），只保留 probe ≤ 最优 ×1.2 的轮次取中位数；
  若仍出现 `full < pos + iter` 这种不可能的不等式，该轮作废。
- **已修**：`ins`/`del` 曾经把 O(n) 建表算进计时（`ins_ns` 被读成"单次插入很慢"）；
  现在构建在计时之外，只计批量部分。
- **已修**：`Store::window_sum` 的默认实现经 `Box<dyn Iterator>`，每窗一次堆分配；
  `VecSorted`/`JumpTuned` 已各自覆盖为直接切片/游标实现，`win-cur` 列才可比。
- 仍未量化：bench 逐段串行测量，段与段之间的缓存/降频漂移没有完全抵消；跨段比较
  （例如"随机查询 vs 窗口"）只应看同一段内的相对值。
