# 性能可疑点清单

> 本文件记录**尚未被测量证实**的性能判断与已验结论。每条注明：现状、验法/结论。
> 行为与不变量见 `src/lib.rs` 文档；数字见 `docs/validation.md`。

## 已修（留作记录，避免回退）

| 问题 | 修法 |
|---|---|
| `range` 上界的线性探上限按窗口大小取（`linear_max*8=64`），64 元窗口被扫两遍 | 改成常量 8 |
| 追加快路径缺失 | 升序插入直接 `push`，省一次二分 |
| 删末尾没有快速路径 | 末元素相等时直接 `pop` |
| `cursor_lower_bound` 命中后仍进"向左找"分支 | 短路 `Equal` |
| `Clone` 会让游标 `id` 复用（正确性坑） | 不实现 `Clone`，文档写明原因 |
| `range` 大步路径重复定位 `hi` | 直接 `block_of(hi)` + 块内二分（或块尾提前返回） |
| `block_of` 的 f64 除法 | 改为乘 `inv_width`；`x/2^k == x*2^-k` 逐位等价（有 fuzz 测试） |
| AoS 的 `(K,E)` 对齐填充 + 扫描碰值载荷 | 主实现改为 SoA（键/值分数组） |
| 编辑指标把 O(n) 建表算进计时 | 构建移到计时外 |
| `window_sum` 默认实现每窗一次 `Box` 分配 | `VecSorted`/`JumpTuned` 各自覆盖 |
| 小数组上块索引打不过二分 | `binary_below = 2048`，小数组直接二分 |

## 已验（结论）

1. **块表大小不是瓶颈**：n=100k/1M 的块宽扫描（scale 0.5–8）无单调趋势；
   n=4M（块表 16 MB，出 L3）随机查询仍 3–4× 领先 Vec。粗化块没有收益，
   自适应块宽方案关闭。
2. **二级锚净收益为负**：n=1M 聚簇随机查询略好（噪声内），顺序查询明显更差
   （多一次网格计算 + 一次加载），稀疏数据几乎不建锚却仍付每查询一次多余加载。
   已实现但**默认关闭**（`with_minor_anchors(false)`）。
3. **`RangeIter` 与 `slice::Iter` 无差异**：窗口拆解的 iter 列两者相同。
4. **随机删除无差距**：成对测量下 Jump 80–89 ns vs Vec 142–155 ns。
5. **`linear_max` 1–64 无可分辨差异**：默认 8 保留。
6. **块表 u16 变体不值得**：块表非瓶颈（见第 1 条）。

## 待验证（按预期收益排序）

1. **时间窗负载缺失**
   - 现状：bench 的窗口按**元素序号**切，聚簇时会切在块中部（对抗性）。
   - 怀疑：真实播放窗按时间切、且与上一窗首尾相接，游标收益被低估。
   - 验法：加"按时间跨度切窗"的负载，比较 `win` 与 `win-cur`。

2. **`RANGE_SCAN_MAX = 8` 是否最优**
   - 现状：固定 8；成对测量下 0/4/8/16/32 无可分辨差异，若继续只能在更稳的机器上
     放大窗口（`--win 1024`）重测。

3. **游标循环的双比较**
   - 现状：循环条件比较一次、退出后再比较一次判断是否超限。顺序查询已明显占优，
     改动收益存疑；可在更稳的机器上用 1e6 次 `find_le_from` 微基准确认。

4. **线性扫的比较成本**（`total_cmp` vs `<`）
   - 只在块内扫描长度变大时才有意义；块扫描默认 ≤8 项，当前影响可忽略。

5. **脏索引期间的查询**
   - 现状：任一写入后所有查询都走二分，直到显式 `rebuild()`。
   - 取决于编辑-查询节奏；若调用方"写 1 次查 1 次"，可考虑按 n 阈值自动 rebuild。

## 测量方法本身的坑

- 每轮先跑固定 CPU 负载（probe），只保留 probe ≤ 最优 ×1.2 的轮次取中位数；
  两档必须**同轮交替**测（先测完一档再测另一档会被状态漂移污染——曾因此
  误报"Vec 删除快 2×"）。
- `ins`/`del` 只计批量部分，构建在计时之外。
- 跨段比较只应看同一段内的相对值（段与段之间仍有缓存/降频漂移）。
- 设备空闲时用 `bench <n> --sweep` 做秒级参数扫描，别为看一个扫描段跑整段基准。
